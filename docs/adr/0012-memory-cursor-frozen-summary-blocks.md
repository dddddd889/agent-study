# 记忆游标：冻结摘要块 + 增量冻结 + 可丢的 sidecar 缓存

## 决策

把摘要压缩从「每次重摘上一版摘要」改成**游标 + 冻结块**模型：一段旧轮被摘成**冻结块**后即定稿、永不再被模型重写；**记忆游标**标记「此位置前的原始轮已冻结」。此后压缩只做**增量冻结**——把游标与最近 K 轮之间新老化的轮摘成一个新块追加到摘要区，游标右移，已冻结块一字不动。冻结块**多块并存**、由 `Agent.frozenCount` 划界（`splitForCompaction` 加起始偏移，把摘要区当不可动前缀跳过）。

- **合并（Q2/Q10）**：冻结块数 ≥ 5 **或** 摘要区占比 ≥ 25%（先到）时，把**全部**冻结块重摘塌成一块、计数归零。低频事件。
- **连贯性（Q3）**：生成增量块时把摘要区作**只读上下文**喂入（看≠改写，退化链不接上）。
- **落盘（Q4/Q5）**：旁挂 `<id>/summary.jsonl`（一行一块 + 末行 `cursorAfter`）作**派生缓存**；主流水 `<id>.jsonl` 仍是唯一真相。续聊校验游标（`≤ 主流水消息数` 且落在轮边界）→ 过则 `[冻结块] + 主流水[cursor:]`，不过/缺失则**丢缓存、退回全量重摘**。只主 agent 落盘（子 agent 不续聊，内存内游标压缩照用）。
- **失败兜底（Q8）**：增量摘要失败时截断，但**只截 `frozenCount` 之后**的逐字轮，冻结块不动。
- **观测（Q9）**：`onCompact.strategy` 扩为 `freeze | merge | truncate`；`/context` 显示冻结块数 + 游标位置。

## 为什么这样

- **真痛点是退化不是省 token**：旧实现 `summary_n = LLM(summary_{n-1} + 新轮)`，摘要被反复重写，早期事实一轮轮漏掉（电话传话）。冻结斩断这条链——这是行为正确性的修复，省 token 只是副产品。
- **退化 vs 增长的调和**：纯冻结会让摘要区无限堆积；纯重摘会退化。选「平时冻结 + 到阈值低频合并」把两端都摁住：退化频率从「每次压缩」降到「每几块一次」。
- **主流水唯一真相**：docs/09 的铁律保护的是**原始流水**。sidecar 明确定性为**可丢的派生缓存**——能重建、能丢弃、丢了自愈，于是这是「乐观加速」而非新故障点；合并时重写 sidecar 也心安理得（只有原始流水神圣）。这也让此改动能分两步落地：先做内存内游标（治运行中退化），落盘为纯增量叠加、不返工。
- **`frozenCount` 而非前缀嗅探**：把冻结边界做成数值字段，`splitForCompaction` O(1) 跳过前缀，根治「冻结块又被划进 old 重摘」的 bug；靠 `[对话摘要]` 前缀判断则脆（用户消息可能撞前缀）。

## 边界与考量

- **子 agent 不落盘**：sidecar 的功能价值是「续聊省重摘」，子 agent 无「下次」——给它写只写不读的文件是把功能设施降格成日志，还逼着重构 `agents/` 布局。故子 agent 保留内存内游标压缩、不落 sidecar。
- **合并保留电话传话的一点点**：全塌成一块每次会重摘整个冻结史，但因低频（阈值封顶）被稀释到几乎无害；不做 B 的「保新鲜」簿记 / C 的层次合并（教学内核里过度设计）。

## 落地

见 [docs/28](../28-memory-cursor.md)。核心：`context.ts` 的切分/截断加 `frozenCount` 偏移；`agent.ts` 的 `compactHistory` 改增量冻结 + 合并 + 只截逐字区兜底,新增 `frozenCursors`/`frozenState`/`loadHistoryWithFrozen`;`session.ts` 的 `writeSummary`/`readSummary` 读写 `<id>/summary.jsonl`;CLI 在 `onCompact` 刷缓存、续聊时校验游标重建。
