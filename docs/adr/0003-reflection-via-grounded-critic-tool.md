# 反思与验证闭环 = grounded 的 `critic` 工具 + 提示驱动循环

## 决策

「反思与验证」不做成代码级的 generate-verify-fix 编排 harness，而是延续「能力即工具 + 提示驱动」：新增一个 **`critic` 工具**（复用子 agent 机制的第二个薄工具），主 agent 在需要时**请** critic 审查产出；「只为 `[严重]` 问题返工、复审、最多约两轮」这个循环靠 system 提示引导，`maxSteps` 兜底。Agent 类零改动。

## 关键：critic 必须 grounded（能自己查真东西）

critic 是一个**带只读查验工具**（`read_file` / `shell` / `http`，去掉 `write_file` / `dispatch_agent` / `critic` 自己）的**上下文隔离**子 agent：

- **有实物**（代码/文件）→ 亲自读代码、grep、跑测试，锚在硬信号上；
- **无实物**（答案/分析/方案）→ 主 agent 把产出文本内联进输入，critic 就事论事判文本（软信号）。

考虑过 **纯文本互评**（critic 无工具、只看主 agent 递来的说法）：便宜但很弱 —— 会被主 agent 的措辞糊弄、看不到真实产物、跑不了测试，退化成「自己人走过场」。所以 critic 必须能独立查验。

## 输入必须同时带「任务 + 产出」

因为上下文隔离，只给结果无法判对错（给 `2` 但不知问的是不是 `1+1`）。critic 输入固定为 `{ task(必填), output(必填), criteria?, artifacts? }`，工具描述明确警告这一点。

## 边界

- **验证的强弱是固有的**：能跑测试的任务硬、纯文本任务软，不硬凹（没法给「这段分析好不好」跑单测）。
- **不滥用**：平凡确定操作（`ls`/看时间/单次读取）不审——反思有成本，「评估比干活还贵」是反模式。
- **防死磕**：只有 `[严重]` 强制返工，`[次要]` 可带注记交付；最多约两轮，仍不过就如实说明剩余问题。
- **复用而非新造**：critic 与 `dispatch_agent` 共享同一 `runSubagent` 核心（隔离/预算/存档/并行/审批透传/优雅收尾全复用），是「子 agent 类型/角色」的一个先行具体实例；通用注册表仍为 TODO。
