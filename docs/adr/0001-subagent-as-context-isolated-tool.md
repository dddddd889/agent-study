# 子 agent 实现为「一个上下文隔离的工具」，而非 Agent 类里的编排逻辑

## 决策

子 agent 模式以一个普通工具 `dispatch_agent` 的形式接入：它的 `run()` 内部 `new Agent(...)`、喂入一段派活 prompt、跑到结束，把**结论**当作 `tool_result` 返回。**Agent 类零改动**，完全复用既有工具循环——与本仓库 `todo_write`、MCP 工具的接入哲学一致（核心不动、能力即工具）。

## 为什么

考虑过的替代方案是 **B：在 Agent 循环里做代码级编排**（主 agent 显式 spawn、调度子 agent，支持依赖图 / 并行）。B 更灵活，但要改动 Agent 核心、破坏「Agent 通用、能力靠工具叠加」的一致叙事，对一个「每步只引入一个核心概念」的教学项目过重。选 A（工具形态）能用一步讲清**上下文隔离**这一个概念。

## 范围与边界（本步刻意的「不做」）

- **不递归**：子 agent 的工具集是「全套 − `dispatch_agent`」，只有主 agent 能派活，杜绝无限递归 / fork 炸弹。
- **不并行**：沿用现有工具循环的串行语义。并行会同时打破实时缩进输出与逐个人工审批（抢 stdout / 抢 stdin），需配套「输出缓冲 + 审批排队」，留作下一步。
- **不共享上下文**：子 agent 看不到主历史、不注入长期记忆；背景由主 agent 写进 prompt。
- **审批透传**：子 agent 内的危险工具仍走主 agent 的 `onApprove`，主/子共享 `always` 白名单。
- **预算独立**：子 agent 有自己的 `maxSteps` / `maxContextTokens`。
- **子档案独立存档**：子 agent 完整历史存到与主会话流水分开的位置，仅供观测；主上下文只留结论。
