# 第 5 步：请求重试 + 指数退避(LLM 层健壮性)

> 这一步不改 agent 内核,而是给 **LLM 调用层**([src/llm.ts](../src/llm.ts))加一层网络健壮性:网关/限流抖动时自动重试,而不是一次失败就让整轮对话挂掉。
> 起因很具体:某次对话报了 `Anthropic API 502`,一个网关抖动就中断了整个 agent 循环。

## 为什么手写 fetch 需要自己补这层

官方 SDK 默认会对 `408/409/429/5xx` 和网络错误**自动指数退避重试**(默认 2 次)。我们这个项目用原生 `fetch`、零依赖,没有这层兜底 —— 一个 502 就 `throw` 了。这一步就是把 SDK 自带的能力手写补上,顺便看清它内部怎么做。

## 哪些该重试,哪些不该

判断逻辑就一句:

```ts
isRetryable = 网络异常 || status === 429 || status >= 500
```

| 情况 | 重试? | 原因 |
|---|---|---|
| 网络异常(fetch 抛错) | ✅ | 连接被拒/超时/重置,大多是临时的 |
| 429 限流 | ✅ | 等一下再来即可 |
| 500/502/503/504/529 | ✅ | 服务端/网关临时故障或过载 |
| 4xx(400/401/403/404/413) | ❌ | **请求本身**的问题(参数/鉴权/过大),重试只是白等 |

「不重试 4xx」是关键:对着一个参数错误重试 3 次,只是把同样的错误慢三倍地报出来。

## 退避节奏:指数 + 抖动

第 n 次重试前等待:

```
delay = min(baseMs * 2^(n-1), capMs) + random(0, baseMs)
```

- 默认 `baseMs=500`、`capMs=8000`:大致 0.5s → 1s → 2s,各自再加一点随机量。
- **抖动(jitter)** 不是装饰:很多客户端同时被同一次故障打到,如果都"恰好等 1s 再重试",会在同一刻**第二次撞车**。加随机量把重试时间打散开。
- **封顶(cap)** 防止指数爆炸等太久。

## 尊重 `Retry-After` 头

429/503 有时会带 `Retry-After` 头,明确告诉你"等 N 秒"。有它就**用它**(同样封顶),没有才退回指数退避。

```ts
delay = min(retryAfter ?? backoff(n), capMs)
```

本步只解析**秒数格式**(`"120"`);HTTP 日期格式(`"Wed, 21 Oct ... GMT"`)很少见,解析失败回退到指数退避 —— 留作 TODO。

## 次数语义

`maxRetries` = **首次失败后额外重试的次数**,默认 **3** → 最坏 `1 + 3 = 4` 次请求,全失败才抛出最后一次的错误。`maxRetries: 0` 表示完全不重试。(与官方 SDK 的 `max_retries` 语义一致,只是默认值不同。)

## 配置与可观测性([src/llm.ts](../src/llm.ts) / [src/cli.ts](../src/cli.ts))

`AnthropicLLMOptions` 新增:

- `maxRetries`(默认 3)
- `retryBaseMs` / `retryCapMs`(默认 500 / 8000;**测试时传 0** 可跳过真实等待)
- `onRetry(info)` 回调:每次重试前触发,带 `attempt / status / error / delayMs`。

库自身**不 `console.log`**(库不该乱打印),而是触发 `onRetry`,由 CLI 决定怎么显示:

```
你> 帮我查点东西
  · 请求失败（502），1.0s 后重试 (1/3)
  · 请求失败（502），2.1s 后重试 (2/3)
AI> ...
```

这样"网关抖动、正在重试"对用户是可见的 —— 否则它只会看起来像卡住了。

## 实现要点

- 把原来的 `fetch + 非 2xx 抛错` 抽成私有方法 `fetchWithRetry(body)`,返回的一定是 2xx 的 `Response`,否则抛错。`complete()` 只负责拼 body 和解析。
- 重试前 `res.body?.cancel()` 丢弃没读的响应体,避免连接泄漏。
- `sleep(0)` 直接 resolve,不排微任务 —— 让 `retryBaseMs: 0` 的测试真正瞬时完成。

## 测试(`bun test`)

[tests/llm.test.ts](../tests/llm.test.ts) 全部 mock `fetch`、`retryBaseMs: 0`(无真实等待):

- **502 后成功**:第一次 502、第二次 200 → 成功,fetch 调 2 次;
- **4xx 不重试**:400 → 立刻抛错,只调 1 次;
- **耗尽重试**:一直 503 → 调 `1 + maxRetries` 次后抛错;
- **网络异常也重试**:第一次 throw、第二次成功;
- **onRetry 被触发**,带状态码;
- **尊重 Retry-After**:`Retry-After: 0` → 用该值而非指数退避。

> 测试踩到的一个坑:`Response` 的 body **只能读一次**,所以 fetch 替身必须每次产出**全新的 Response**(用工厂函数 `() => new Response(...)`),不能复用同一个对象 —— 否则重试时读到的是已被消费/取消的 body。
