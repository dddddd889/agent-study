# 领域文档（Domain Docs）

各个工程类 skill 在探索代码库时，应当如何使用本仓库的领域文档。

## 探索前先读这些

- 仓库根目录的 **`CONTEXT.md`**，或
- 仓库根目录的 **`CONTEXT-MAP.md`**（若存在）——它会指向每个上下文各自的 `CONTEXT.md`，按主题读取相关的那几个。
- **`docs/adr/`** —— 阅读与你即将动手的区域相关的 ADR。在多上下文仓库里，还要看 `src/<context>/docs/adr/` 下的上下文级决策。

如果这些文件都不存在，**就静默继续**。不要提示它们缺失，也不要一上来就建议创建。`/domain-modeling` skill（经由 `/grill-with-docs` 和 `/improve-codebase-architecture` 触发）会在术语或决策真正被确定时按需创建它们。

## 文件结构

本仓库是**单上下文（single-context）**仓库：

```
/
├── CONTEXT.md
├── docs/adr/
│   ├── 0001-....md
│   └── 0002-....md
└── src/
```

（多上下文仓库则在根目录放一个 `CONTEXT-MAP.md`，指向 `src/<context>/` 下各自的 `CONTEXT.md`。本仓库不使用这种布局。）

## 使用术语表里的词汇

当你的产出里出现某个领域概念（issue 标题、重构提案、假设、测试名等），使用 `CONTEXT.md` 里定义的术语。不要漂移到术语表明确避免的同义词。

如果你需要的概念还没在术语表里，这就是个信号——要么你在发明项目并不使用的说法（请重新考虑），要么存在真实的空缺（记下来交给 `/domain-modeling`）。

## 标记 ADR 冲突

如果你的产出与某条已有 ADR 相矛盾，请显式指出，而不是悄悄覆盖：

> _与 ADR-0007（……）相矛盾——但值得重新讨论，因为……_
